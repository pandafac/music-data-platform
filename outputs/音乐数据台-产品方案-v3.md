## 1. 产品定位

### 1.1 一句话定位

**把 QQ音乐 的榜单快照，变成一个随时可查的音乐数据台——查得到轨迹，看得懂变化，追得动记录。**

### 1.2 定位的依据

音乐平台给用户的是**时刻**：今天的榜单上谁第几。

数据迷要的是**轨迹**：这首歌空降第几、在榜几周、中间有没有掉出去、什么时候回榜、最高到过第几。

这中间是断的。数据迷现在的实际动作是：打开 QQ音乐 看榜单（只有今天的快照）→ 去 B站 搜 UP主做好的走势视频（要等更新、只有别人做的事）→ 再去 Spotify 查国际数据（口径还对不上）。**三个地方、三套口径、还依赖别人。**

产品要省掉的，就是这一整串动作。

### 1.3 目标用户

| 层级 | 是谁 | 产品对他意味着什么 |
| --- | --- | --- |
| 核心 | 数据迷 | 一个专业、准确、可深挖的数据工具（替代手工扒数据） |
| 外围 | 泛音乐用户 | 一个好看、好懂、有故事的数据入口 |
| 生产者 | 内容创作者 | 一键产出走势图与文案的素材源 |

**关键判断：专业与大众不矛盾。** 能力是一套，呈现分层次——默认给结论，想深挖的再展开。同一个功能，深浅自取。

### 1.4 我们是什么 / 不是什么

| 我们是 | 我们不是 |
| --- | --- |
| 数据迷的查数据入口 | 粉丝对线工具（引战，不做） |
| 轨迹与记录的可视化工具 | "谁更红"的裁判（单平台做不到） |
| AI 辅助的数据阅读器 | 又一个榜单列表页（QQ音乐已有） |
| 数据驱动的发现工具 | 音乐资讯/热点聚合流 |

## 2. 问题与机会

### 2.1 现状痛点

- 数据存在，但**散**：榜单页只有当期快照，历史轨迹无处可查。
- 口径不透明：各榜统计方式不同，用户不知道数字怎么来的。
- 依赖他人：想看走势只能等 UP主 做视频。
- 跨平台割裂：国际榜单要跑到 Spotify / 公告牌官网，口径与中文平台不通。

### 2.2 社区验证

B站、抖音存在大量自制内容：「QQ音乐歌手排名变化史」「歌手总榜登顶天数」「KPOP 音乐指数 TOP1000」。**有稳定受众，全部手工制作。** 需求真实，供给空白。

### 2.3 机会

1. **供给空白**：平台内没有面向歌手/单曲的可交互轨迹与对比功能。
2. **数据资产**：QQ音乐 拥有站内榜单、音乐指数、由你榜历史，并已收录全球榜（公告牌/Melon/UK/公信榜）。
3. **AI 补位**：把"找数据、算数据、画数据、读数据"四件事的复杂度一次性打下来。

**核心价值主张：让音乐数据像票房数据一样，人人可查、可读、可追。**

## 3. 核心概念与数据模型

### 3.1 核心对象：轨迹（Chart Run）

产品的最小知识单元不是"排名"，而是**一条轨迹**——某个作品在某个榜单上，从进榜到出榜的完整序列。

```
3 → 2 → 1 → 1 → 2 → 5 → 8 → 出榜 → 12 → 15 → 出榜
```

轨迹可以归属到三个层级：**单曲 / 歌手 / 专辑**（三者都要做）。

### 3.2 事件词汇表

| 事件 | 定义 |
| --- | --- |
| 空降（debut） | 首次进榜的名次 |
| 出榜（exit） | 掉出榜单 |
| 回榜（re-entry） | 出榜后重新进榜 |
| 峰值（peak） | 历史最高名次 |
| 在榜周期数 | 累计在榜的周期数（单位随榜单而定：日更榜记"天"，周更榜记"周"） |
| 连冠 | 连续位居第一的周期数 |
| 在榜最久 | 该榜历史最长在榜记录 |
| 破纪录 | 触发上述纪录的历史性时刻 |

### 3.3 数据模型（实体关系）

```
Artist(id, name, aliases[], region, genres[])
   |
   +-- Work(id, title, type[单曲/专辑], artist_ids[], release_date)
   |      +-- WorkVersion(id, work_id, platform_id, title_raw,
   |                      flags[原版/重录/翻唱/现场/混音/Deluxe/不同时长])
   |
Chart(id, name, category[热度/地区/曲风/场景/全球], update_freq)
   |
ChartEntry(chart_id, date, work_id, rank, index_value,
           prev_rank, weeks_on_chart, status[在榜/未上榜/无数据])
   |
Milestone(subject_id, type[空降/峰值/连冠/在榜最久/破纪录], value, date)
```

**要点**：`Work` 与 `WorkVersion` 分离，是所有统计口径准确的前提。

## 4. 数据方案

### 4.1 数据来源

| 类别 | 内容 | 说明 |
| --- | --- | --- |
| 站内榜 | 热歌榜、飙升榜、新歌榜、流行指数榜等 | 热歌榜为每日更新 |
| 全球榜 | 美国公告牌榜、韩国 Melon 榜、英国 UK 榜、日本公信榜 | 已收录于 QQ音乐 站内 |
| 历史归档 | 由你榜历史期数、历年榜单 | **产品的护城河，TME 独有** |
| 销量（待评估） | 数字专辑销量数据 | 数据迷语境下的"票房"对应物 |

### 4.2 三层归一化

**（1）歌手实体归一化**
合并别名、中英文名、重复条目（如"泰勒·斯威夫特" = "Taylor Swift"），输出唯一歌手实体。

**（2）作品归一化（最关键）**
实测曲库存在大量多版本条目，例如：

```
All Too Well (10 Minute Version|Taylor's Version|Explicit)
```

不处理会导致：作品数虚高、热度被版本策略放大、对比不公平。

规则：

1. 按「歌名主干 + 歌手 + 曲目指纹/ISRC」分组；
2. 组内热度**加总**到唯一 Work；
3. 另存字段「版本数」，可展示，不参与总量排名；
4. 提供开关「是否包含重录版/翻唱版/不同时长版」，默认合并。

**（3）指标归一化**
消除"歌多就赢"的偏差：除绝对值外必须同时给出相对值（如"在榜歌曲 / 作品库总数"）。

### 4.3 数据缺失三态

| 状态 | 含义 | 展示 |
| --- | --- | --- |
| 在榜 | 有数据且在榜 | 正常显示 |
| 未上榜 | 有数据但当期未进榜 | 显示"未上榜" |
| 无数据 | 未上架/无版权 | 标注"暂无数据"，**不参与计算** |

绝不把"无数据"当 0，也绝不把"未上架"读成"不红"。

### 4.4 口径与来源标注

所有数据展示处标注：**来源 / 统计范围 / 取数时间戳 / 数据起始时间**。
这既是数据迷的刚需，也是产品的可信度底座。

### 4.5 榜单"主战场"匹配机制

QQ音乐 的榜单合计约 40 个，全量堆给用户必然造成过载。解决方案是自动判断"这个歌手该看哪些榜"：

**规则给默认 → 数据做修正 → 用户能覆盖**

| 歌手特征 | 默认主场榜 |
| --- | --- |
| 华语/内地 | 热歌榜、内地榜 |
| 粤语/香港 | 香港地区榜、TVB 劲歌金榜 |
| 台湾 | 台湾地区榜、KKBOX 榜 |
| 韩语 | 韩国榜、Melon 榜 |
| 日语 | 日本榜、公信榜 |
| 欧美 | 公告牌榜、UK 榜、欧美榜 |
| 说唱 | 说唱榜 |
| 电音/舞曲 | 电音榜、DJ 舞曲榜 |
| 影视/综艺 | 影视金曲榜、综艺新歌榜 |
| 国风 | 国风热歌榜 |
| 动漫/游戏 | 动漫音乐榜、游戏音乐榜 |

规则判断主场（按语种/地区/曲风/场景）；数据做修正（某歌手意外在别的榜爆了，自动捞进来——"意外"正是数据迷最爱的发现）；用户可自定义追加。

## 5. 指标体系

### 5.1 六维

| 维度 | 含义 | 归一化口径 |
| --- | --- | --- |
| 热度总量 | 绝对规模 | 作品平均指数（非总和） |
| 峰值高度 | 最高水平 | 历史最高名次 / 最高指数 |
| 持续性 | 在榜多久 | 累计在榜周期数 |
| 稳定性 | 波动大小 | 指数波动率（越小越稳） |
| 爆发力 | 上涨速度 | 指数上升速率、飙升榜表现 |
| 覆盖广度 | 上过多少榜 | 上榜数量与榜单层级 |

### 5.2 自定义权重

产品**不给**综合总分。权重由用户拖动，雷达图实时变化。

三重收益：产品不裁决谁更红；无不透明权重即无争议；拖权重本身就是玩法。

### 5.3 跨榜对比的相对表现口径

榜单跨到全球后，绝对名次不可直接比较（Melon 第一 与 热歌榜第一 不等价）。因此跨榜、跨地区对比统一采用**相对表现**：

- 该榜内的排名百分位；
- 在榜周期占该榜统计周期的比例；
- 峰值维持周期数。

**比的是"各自在自己赛道上跑得多好"，而不是"谁的数字大"。**

## 6. AI 方案

### 6.1 角色与边界

**AI 负责"怎么讲"，不负责"讲什么"。**

| 层 | 来源 | 性质 |
| --- | --- | --- |
| 数据事实层 | 系统从自有数据计算 | 准确、可验证、可作为结论依据 |
| AI 叙事层 | AI 生成 | 解释与表达，不是事实来源 |

**这一步是产品可信度的关键。** 若让 AI 自行检索事实，来源模糊、可能出错；而数据产品一旦有一个数字不实，整体可信度即崩塌。同时，把"检索事实"交给外部，等于放弃历史榜单归档这一独有资产。

### 6.2 三类能力

1. **查询**：自然语言 → 结构化数据（"这首歌空降第几？待了几周？中间掉出去过吗？"）
2. **叙事**：把事实讲成人话（一句话标题、背景注解）
3. **比较**：把两个对象的相对表现并列呈现

### 6.3 明确不做

- 不预测未来排名（不可验证）
- 不裁决"谁更红"
- 不生成带倾向性的结论
- 不把外部检索结果当作数据事实

## 7. 产品结构与页面

### 7.1 信息架构

```
QQ音乐功能区入口
   └── 音乐数据台（独立页面）
         ├── 首页：数据现场（今日 / 往年今日）
         ├── 轨迹页（单曲 / 歌手 / 专辑）
         ├── 对比页（歌手 vs 歌手 / 作品 vs 作品）
         └── 历史页（往年今日时间轴）
```

### 7.2 首页：数据现场

第一屏只做一件事：**让用户想点开那条线。**

```
+-------------------------------------+
|  () 数据现场       [今天] [往年今日] |
|                                     |
|   这首歌空降第 3，一路掉出去，       |
|   第 12 周它又回来了。               |
|                                     |
|    (*)                    [ 回榜 ]   |
|    /\                                |
|   /  \__                 ____/       |
|  /      \____________/               |
|  空降                                |
|                                     |
|  《歌名》· 歌手 · 在榜 34 期         |
+-------------------------------------+
|  [搜索] 想知道哪首歌的榜单轨迹？     |
+-------------------------------------+
（下一屏）榜单速览 -> 记录墙
```

组成：一条会动起来的走势曲线 + 事件标记光点 + 一句人话标题 + 一行来源信息。

**内容类型（今日）**：今日空降 / 破纪录 / 最猛飙升 / 黑马回榜。
**内容类型（往年今日）**：五年前的今天、三年前的今天，逐条回溯。

**为什么这样定**：

- 一眼说明产品是什么，无需解释；
- 同时满足数据迷与路人（同一块内容两种深度）；
- "今日"属性形成每日回访；
- 排名曲线自带视觉张力，动画点亮即足够亮眼；
- 可滑动、有动效，呼应"让音乐玩起来"。

### 7.3 轨迹页

| 区块 | 内容 |
| --- | --- |
| 头部 | 作品信息、当前状态、来源与取数时间 |
| 轨迹主图 | 排名曲线（反向 Y 轴，第 1 在顶部）；空降/回榜/出榜光点标注；出榜区间以断线呈现 |
| 轨迹文本 | 3-2-1-1-2-5-8-出-12 序列 |
| 关键指标 | 空降位、峰值、在榜周期数、回榜次数 |
| 微调控件 | 时间窗、榜单切换、版本合并开关 |
| 关联榜 | 主场榜上的其余轨迹 |
| AI 解读 | 事实 + 人话说明 |

**歌手/专辑层**：把名下作品的轨迹聚合呈现（在榜作品数、合计在榜周期、最高峰值），并可下钻到单曲。

### 7.4 对比页

- 选择两个对象（歌手 / 作品）
- **榜单并集展示 + 缺失标注**（不隐藏、不补零）
- 六维数值对照 + 自定义权重雷达
- 跨榜场景自动切换为"相对表现"口径
- 一键生成分享卡（带来源、口径、时间戳）

### 7.5 历史页（往年今日）

- 年份时间轴纵向排列，逐年回溯该日期的榜单事件
- 交互隐喻：**横向切换事件，纵向切换年份**——像翻一本音乐数据年鉴
- 仅呈现数据事件（榜单事实），不引入外部资讯
- 周更榜按期对齐（对到同一"期"而非同一日），并在界面上标明是"第 N 期"

### 7.6 视觉风格

沿用 QQ音乐 设计语言：品牌主色、卡片式布局、深色模式适配。数据可视化采用轻量线条与光点，避免报表感。

### 7.7 追更与订阅

- 关注歌手 / 作品 → 上榜、回榜、破纪录时提醒
- 提供"数据周报"：本周该对象的关键事件汇总
- 作用：把"一次性查询"变成"持续回访"，与首页"今日"形成闭环

## 8. 交互设计

### 8.1 核心原则：自然语言是入口，结构化是精修

二者不是两个并列模式，而是**同一张数据卡的两层**：

1. 用户问一句（或点一条头条）→ 返回一张数据卡（图 + 结论）；
2. 卡上提供微调控件（时间窗、榜单、版本合并、六维权重）；
3. 拖动即原地重算，无需重新提问。

**分工**：自然语言负责把用户送到答案面前；结构化负责让用户拨弄答案。从"随便问问"到"专业开挖"是渐进、无缝的。

### 8.2 关键交互模式

| 交互 | 隐喻 |
| --- | --- |
| 首页左右滑动 | 切换数据事件 |
| 历史页上下滑动 | 切换年份 |
| 拖动权重条 | 雷达图实时变化 |
| 点击曲线上光点 | 展开该事件详情 |
| 开关"包含重录版" | 口径实时切换 |

## 9. 与现有功能的关系

| 现有能力 | 它做什么 | 本产品做什么 |
| --- | --- | --- |
| 音乐指数 | 单曲维度、约半年走势 | 轨迹归档 + 跨榜聚合 + 对比 |
| 由你榜 | 官方周榜、历史得分 | 复用其数据，做交互与叙事 |
| 巅峰榜 | 各类榜单排名 | 作为数据源，不重复展示 |
| 我的歌手榜 | 个人收听排行 | 与"平台热度"明确区分 |

**一句话**：现有的是"看单曲数据"，本产品做的是"查得动轨迹、比得了对象、追得住记录"。

## 10. 评审三维度对照

| 维度 | 回答 |
| --- | --- |
| 用户价值 | 数据迷的查数据刚需长期靠手工与他人生成内容满足；社区已验证需求，平台内供给空白 |
| 可行性 | 数据在 TME 内部；Demo 可用公开榜单接口 + 样例历史数据；技术路径清晰 |
| 创新性 | 轨迹归档 + 主战场匹配 + 相对表现口径 + 自定义权重 + 事实/叙事分离的 AI 用法 |

**呼应赛题"让音乐玩起来"**：数据现场、翻年鉴式回溯、拖权重、可滑动的数据故事。

## 11. Demo 方案（本次黑客松）

### 11.1 Demo 范围

聚焦一条完整可交互的主线，不追求全量功能：

1. 首页「数据现场」（今日 + 往年今日切换、走势线动画、人话标题）
2. 轨迹页（真实当前榜单数据 + 示例历史轨迹）
3. 对比页（并集展示 + 六维雷达 + 权重拖动）

### 11.2 技术方案

| 层 | 选型 |
| --- | --- |
| 前端 | React + Vite + TypeScript |

1. **图例**：明确哪块颜色对应哪位（原来完全没有，是硬伤）；
2. **一句话结论**：把多边形翻译成"谁在几个维度领先、分别是哪些"，权重一变结论就变；
3. **一键预设**：均衡 / 只看峰值 / 只看常青 / 只看覆盖——比拖六个滑块直观得多，一秒就能看到"权重改变结论"；

## 附录 D：外部热点层设计

### D.1 为什么必须独立成层

热点是**背景注解**，不是数据事实。一旦把它混进事实层，出现一次误报就会拖垮整个产品的数据可信度。因此明确三层并列、互不越界：

| 层 | 来源 | 是否参与计算 | 标注 |
| --- | --- | --- | --- |
| 数据事实 | 平台榜单数据 | 是 | 【事实】 |
| 外部热点 | 第三方平台抓取 | **否** | 【热点】+ 来源 + 日期 |
| AI 解读 | AI 生成 | 否 | 【解读】 |

### D.2 抓取实现

- **脚本**：`tools/fetch-hot.mjs`，多源抓取（微博热搜 / 抖音热榜 / 百度热搜），按音乐关键词过滤，输出 `demo/hot.json`，字段含 `fetchedAt`、各源扫描与命中数、命中条目。
- **运行**：`node tools/fetch-hot.mjs`
- **前端**：优先读取 `hot.json`（http 环境）；读取失败时回退到内置快照，保证 `file://` 双击打开也能用。
- **界面**：首页"外部热点追踪"条展示实时命中项、来源、抓取时间，并固定声明"外部信息，不计入榜单数据"。
- **界面位置（修订）**：热点**只出现在歌曲内页的 AI 解读里**，作为该曲走势的背景注解；首页不再展示热点条。原因：热点是"某首歌为什么动"的注解，脱离具体作品去展示会退化成资讯流，偏离产品定位。

### D.3 实测发现（影响可行性判断）

首轮实抓结果：

| 来源 | 扫描 | 音乐相关命中 |
| --- | --- | --- |
| 微博热搜 | 50 | 0 |
| 抖音热榜 | 50 | 3（如"李荣浩临沂演唱会"） |
| 百度热搜 | — | 结构变动，本轮 0 |

**结论：综合热榜几乎不含音乐事件。** 要真正做好音乐热点追踪，需要垂直来源：

- 艺人 / 厂牌 / 颁奖礼官微（格莱美、MAMA 等）
- 音乐垂类榜单（B站音乐区、抖音音乐榜等）
- 关键词订阅式检索（"演唱会""新歌""专辑"）
- 平台内信号（飙升榜突变、搜索量突增）

因此热点层的正确定位是**辅助注解**，而不是产品支柱；这也解释了为什么"谁因为格莱美表演热度大升"这类信息必须人工或垂直源确认，不能靠综合热搜自动获得。

### D.4 表达纪律

1. 热点与数据变化只能表述为**同期**，不能表述为**因果**（界面文案已按此约束生成）。
2. 每条热点必须携带来源与日期，缺一不展示。
3. 示例数据必须显式标注"非真实事件"，不得伪装成真实新闻。

### D.5 新增样例验证

加入两个跨市场样例后，主战场机制与跨榜口径得到验证：

| 作品 | 歌手 | 主场榜 | 轨迹单位 |
| --- | --- | --- | --- |
| Whiplash | aespa | 韩国 Melon 榜 | 周 |
| The Fate of Ophelia | Taylor Swift | 美国公告牌榜 | 周 |

两者在轨迹页会显示各自的榜单与单位（周榜记"周"、站内日榜记"天"），AI 解读中的口径提示也会按榜单自动切换（站内榜提示"仅统计站内行为"，外部榜提示"口径不同、不可直接比较"）。

# 音乐数据台 · 产品升级方案

> 本文取代早先两版（《全面升级方案》《参赛升级方案》）——它们分别错在"按产品完整度排序"和"按工期砍需求"。
> 这一版**按用户价值排序**，并且**明确划清了分工**。

---

## 0. 这份方案怎么分工（先说清楚各自的边界）

| 谁 | 负责什么 | 为什么 |
| --- | --- | --- |
| **我（结构侧）** | 产品定位、信息架构、功能定义、数据逻辑与口径、内容文案、状态穷举、约束与验收标准 | 这些是"定义问题"的活，可以推演、可以论证 |
| **看山工作台（视觉侧）** | 视觉语言、色彩与字体、图形与图表风格、视觉资产、动效质感 | **视觉不是我的强项**——我不应该替它规定"长什么样"，只应该把"必须满足什么"说清楚 |

**因此本文第 4 章不是设计规范，而是一份设计简报（brief）**：给它目标、内容清单、约束和反面清单，让它去探索和决定审美。

## 1. 用户与价值

### 1.1 用户是谁

| 用户 | 他要什么 | 他现在的做法 |
| --- | --- | --- |
| **数据迷**（核心） | 看清一首歌/一个歌手的完整轨迹、纪录、对比 | 开榜单页看当期 → 去 B站 搜 UP主 做的走势视频 → 再去外站查国际榜；**三个地方、三套口径、还依赖别人** |
| **歌迷**（外围） | 关心自己喜欢的歌手最近怎么样 | 只能看到"今天第几"，看不到变化 |
| **内容创作者**（生产者） | 找选题、出素材 | 手工整理数据、手工做图 |

### 1.2 一句话与三个承诺

> **把榜单快照，变成随时可查的音乐数据台。**

三个承诺（产品的立身之本）：

1. **查得到轨迹** —— 空降、在榜、出榜、回榜，一条线讲清一首歌的故事；
2. **说得清口径** —— 每个数字都能告诉你它从哪来、怎么算、能不能比；
3. **不替你下结论** —— 对比呈现事实，谁强谁弱由你判断。

### 1.3 用户体验的七个环节 × 当前完成度

这是本方案的核心诊断表：**按用户真实旅程拆，逐环节打分**。

| 环节 | 用户想做什么 | 现状 | 完成度 |
| --- | --- | --- | --- |
| **① 发现** | 打开就知道"今天有什么值得看的" | 只有一条头条 + 几条轮播 | **40%** |
| **② 查询** | 搜任何歌或歌手，立刻拿到完整轨迹 | 只有 12 首示例曲、1 个真实榜单 | **20%** |
| **③ 对比** | 在同一口径下比较两个对象 | 歌手维度的六维对比 + 可调权重 | **60%** |
| **④ 追踪** | 我关注的对象有变化时告诉我 | 只有一句硬编码的"已关注 3 位歌手" | **5%** |
| **⑤ 收藏** | 存下来随时回看 | 可收藏、可删除，有列表 | **70%** |
| **⑥ 产出** | 把看到的变成能分享的东西 | 按钮只弹提示，没有产出 | **5%** |
| **⑦ 信任** | 随时知道数据从哪来、什么口径 | 底部一行小字 | **35%** |

**结论：产品在最关键的两头都是空的——入口（发现）和出口（产出）。**

### 1.4 按用户价值排序的差距清单

| 优先级 | 差距 | 用户损失 |
| --- | --- | --- |
| 🔴 1 | **产出为零**：看完什么都带不走 | 数据迷的天性是分享，这条断了，产品就没有传播 |
| 🔴 2 | **入口太弱**：打开后不知道该看什么 | 没有日活，工具变成一次性查询 |
| 🔴 3 | **可查范围太小**：只有 12 首歌 | 定位直接不成立 |
| 🟠 4 | **没有追踪**：关注了也没有回音 | 没有回访理由 |
| 🟠 5 | **一首歌只能看一个榜** | 真实场景是"这首歌同时在三个榜上"，现在看不到 |
| 🟠 6 | **纪录是假的**：记录墙写死文案 | 纪录是数据迷最上瘾的部分，浪费了 |
| 🟠 7 | **信任层没做成功能**：口径只在小字里 | 数据迷最在意可信度，却看不到 |
| 🟡 8 | **AI 只是模板填空** | 问不出自己想问的 |
| 🟡 9 | **视觉没有记忆点**（交给看山） | 不像一个专业工具 |

## 2. 数据现实：可做与不可做

升级方案必须建立在**真能拿到的数据**上。以下为实测结论。

### 2.1 能真实拿到

| 数据 | 实测结果 |
| --- | --- |
| 巅峰榜·热歌 | ✅ 真实，每日更新，**300 首** |
| 巅峰榜·新歌 | ✅ 真实，每日更新，100 首 |
| 巅峰榜·流行指数 | ✅ 真实，每日更新，100 首 |
| 飙升榜 | ✅ 真实，每日更新，100 首 |
| 巅峰榜·欧美 | ✅ 真实，每周更新，100 首 |
| 专辑封面 | ✅ 已实测 12/12 命中 |
| 外部热点 | ✅ 微博 / 抖音 / 百度热榜 |

**合计 5 个榜单、700 条真实上榜记录**（歌名、歌手、名次、封面、更新时间、涨跌均为真）。

### 2.2 拿不到

| 数据 | 为什么 |
| --- | --- |
| **历史轨迹归档** | 公开接口不支持按日期回溯（带 date 参数直接报错），逐期快照只能从今天起累积 |
| 站外官方数据、销量、巡演、奖项 | 无公开接口 |

### 2.3 这个限制该怎么讲（重要）

**"拿不到历史"不是产品的缺陷，而是"这件事应该由平台自己做"的论据。**

> 外部产品受限于公开接口，只能看到"此刻"，拼不出"轨迹"；
> 平台拥有逐年逐期的榜单归档，这正是它独有的数据资产。
> 产品形态已经被 Demo 验证，平台把已有历史接进来即可上线。

同时，Demo 里的一切数据都要**如实标注来源与性质**：真实的就说真实，演示的必须写"演示"。**不假装有更早的数据**，反而更能建立信任。

## 3. 功能升级（按用户价值排序）

### F1　分享产出 ⭐ 最高优先

**对应环节**：⑥ 产出（现状 5%）

**现状**：唯一的分发动作是"生成对比卡"，点下去只弹一个提示，**什么都没产出**。

**目标**：一键把"我看到的"变成"我可以发出去的"。

**为什么它排第一**：数据迷的天性就是分享——看到一个惊人的走势，第一反应是截图发群。这个动作断了，产品就永远只能自娱自乐。而且它是**唯一能带来新用户的环节**。

**三种卡型**：

| 卡型 | 内容 | 场景 |
| --- | --- | --- |
| **轨迹卡** | 单曲曲线 + 空降/峰值/出榜/回榜 + 关键数字 | "这首歌的走势太离谱了" |
| **对比卡** | 两个对象的维度对比 + 一句结论 | "同一口径下比一比" |
| **纪录卡** | 徽章 + 纪录名 + 数字 + 作品 | "十连冠诞生了" |

**必须包含**：数据来源、取数时间、口径说明。**这不是装饰，是产品的立场**——一张能被转发的图，必须自带"经得起追问"的证据。

**验收**：点一下能拿到图；图上数字与页面完全一致；图上有来源与口径。

---

### F2　发现页 2.0（首页重做）

**对应环节**：① 发现（现状 40%）

**现状**：一条头条 + 四条写死的轮播，用户打开后"看完这条就没事干了"。

**目标**：让首页变成**"今天值得看的数据现场"**，而不是一个横幅。

**关键设计**：

1. **多条事件，按类型分区**（不是一条大横幅）：
   - **今日空降**：新进榜的高位作品
   - **破纪录**：新诞生的纪录（接 F6）
   - **最猛异动**：名次涨跌最剧烈的
   - **回榜**：掉出去又回来的
2. **每条都是"一句话 + 一张缩略曲线"**，点进去是完整轨迹；
3. **时间维度可切换**：今天 / 本周 / 本年（取代现在空壳的"往年今日"）；
4. **顶部保留一条"主推"**，但只占约 1/3 屏高——现在它占满了整屏。

**为什么这样改**：数据迷的爽点是"发现"，是"今天又有什么有意思的事"。一条轮播撑不起这个功能。

**验收**：首页一屏内至少能看到 3 类事件、共 6 条以上内容，且全部可点。

---

### F3　数据规模化（把可查范围从 12 首扩到 700 条）

**对应环节**：② 查询（现状 20%）

**现状**：12 首示例曲，且只有热歌榜有真实数据。

**目标**：**接入 5 个真实榜单、700 条上榜记录**（接口已实测可用，见附录 A）。

**用户价值**：这是"可查"这个词的前提。数据迷打开的第一件事就是搜自己想看的那首歌——搜不到，产品就结束了。

**关键设计**：

1. **榜单页**：每个榜单一个列表页，展示真实前 50 首（封面 + 名次 + 涨跌 + 歌手），可点进任意歌曲；
2. **搜索**：曲名 / 歌手 / 拼音首字母；
3. **区分标注**：当期名次（真实）与历史轨迹（演示）在界面上必须一眼可分；
4. **每榜标注数据起始时间**，不假装有更早的数据。

**验收**：能搜到任意在榜歌曲并进入其轨迹页；榜单页 5 个榜都可访问。

---

### F4　追踪与提醒

**对应环节**：④ 追踪（现状 5%）

**现状**：个人页写着"已关注 3 位歌手"，但那是硬编码的，没有任何功能。

**目标**：关注 → 有变化时告诉我。

**关键设计**：

1. 歌手页 / 歌曲页加"关注"；
2. 关注后在首页顶部出现**"我的关注"区**：显示关注对象的最近变化（新进榜、回榜、破纪录、名次异动）；
3. **本地模拟即可**（Demo 阶段不接推送），但要有"如果上线会怎么提醒"的说明；
4. 个人页展示真实的关注列表，可取消。

**为什么重要**：这是**唯一的回访理由**。没有追踪，工具就是一次性的。

**验收**：关注后能在首页看到该对象的变化；取消后消失。

---

### F5　多榜并列（一首歌在多个榜上的同期表现）

**对应环节**：② 查询 / ③ 对比

**现状**：一首歌只能看一个榜。

**目标**：一眼看到"这首歌同时在几个榜上是什么状态"。

**关键设计**：

1. **榜单条带图**：横轴时间，每行一个榜单，色块深浅表示名次高低，行内标出最高点；
2. **跨榜对比必须用相对表现**（排名百分位 / 在榜占比），并明确写出**不同榜单名次不可直接比较**；
3. 歌曲页顶部提供榜单切换，主战场榜（按语种/地区自动匹配）为默认。

**为什么重要**：这是产品声称的"护城河"之一，现在只做到了 30%。

**验收**：一首歌能在一屏内看到 ≥3 个榜的表现，且口径说明清晰。

---

### F6　纪录引擎（把假记录变成真纪录）

**对应环节**：① 发现 / ② 查询

**现状**：记录墙四条纪录是写死的文案，和用户查的歌没有任何关系。

**目标**：纪录由数据算出来。

**要实现的纪录**：

| 纪录 | 计算方式 |
| --- | --- |
| 空降冠军 | 轨迹首期排名 = 1 |
| 连冠 N 期 | 连续且等于 1 的排名最长长度 |
| 在榜最久 | 累计在榜期数最大 |
| 最猛爬升 | 相邻两期名次提升最大 |
| 强回榜 | 出榜后回归名次最高 |
| 长青单曲 | 在榜期数超阈值且当前仍在榜 |

**关键设计**：

- 首页记录墙改为**"最近诞生的纪录"**，有时间感；
- 每条纪录可点进对应作品；
- 纪录配**成就徽章**（视觉资产，交给看山）。

**为什么重要**：票房榜让人上瘾的从来不是"当前票房"，而是"**史上最快破亿**"。纪录是情绪的爆点。

**验收**：改一条轨迹数据，纪录墙随之变化；每条可跳转。

---

### F7　数据说明（把信任做成功能，而不是一行小字）

**对应环节**：⑦ 信任（现状 35%）

**现状**：数据来源、口径、边界只是页面底部一行灰色小字。

**目标**：让"我在哪拿的数据、怎么算的、能不能比"**随时可查、一眼看懂**。

**关键设计**：

1. 每个数据区块旁有"ⓘ"，点开显示：数据来源 / 更新时间 / 计算方式 / 可比性说明；
2. 独立的**"数据说明"页**：哪些是真的、怎么拿的、哪些是演示、为什么历史拿不到、正式落地怎么补；
3. 用**统一的三色标签**贯穿全站：
   - 【事实】来自榜单数据
   - 【热点】来自外部平台，**不参与计算**
   - 【解读】AI 生成

**为什么重要**：这是这个产品区别于所有"看图说话"类产品的**唯一理由**。别的产品不告诉你这些——我们把"讲清楚"本身做成功能。

**验收**：任意数据区块都能就地展开口径说明；三色标签全站一致。

---

### F8　AI 从"模板填空"升级为"检索层"

**对应环节**：② 查询

**现状**：关键词匹配 + 模板回答，超出预设就问不出来。

**目标**：**用自然语言问任何数据问题**。

**关键设计**：

1. 用函数调用（Function Calling）替代关键词匹配，暴露能力：`search_song / get_track / compare / list_records / get_chart`；
2. 每次回答附**"依据"折叠区**，说明用了哪些数据；
3. 答不出来时给**三个可行问法**，而不是说"答不了"。

**硬约束（不可放宽）**：事实只来自系统，AI 不检索事实、不编造数字；热点只做背景（只能说"同期"，不能说"因为"）；**不预测排名、不下"谁更红"的结论**。

**验收**：任意数据类问题能得到有依据的回答，且能追溯到数据来源。

---

### F9　收藏页深化

**对应环节**：⑤ 收藏（现状 70%，最高分，改动最小）

**现状**：已可收藏、可删除、有列表和缩略走势。

**小幅补强**：

- 收藏对象支持**歌手**（现在只能收藏歌曲）；
- 加"我的数据资历"：收藏 N 条 / 关注 M 位（数据迷喜欢收藏感）；
- 收藏列表支持按榜单筛选。

---

### 3.1 依赖关系（决定做的顺序）

```
F3 数据规模化（基础，其他都依赖它）
   ├── F2 发现页 2.0（需要足够数据才有内容）
   ├── F5 多榜并列（需要多榜数据）
   ├── F6 纪录引擎（需要轨迹数据）
   └── F1 分享产出（需要真实数据填进卡里）
F7 数据说明（独立，随时可做）
F4 追踪（依赖 F3）
F8 AI 检索（依赖 F3，但价值高）
F9 收藏深化（独立，最省事）
```

**建议顺序：F3 → F1 → F7 → F2 → F6 → F4 → F5 → F8 → F9。**

## 4. 视觉升级：设计简报（交给看山）

### 4.1 先说清楚：这部分我不该替它决定

我可以把"要放什么、给谁看、必须满足什么"讲清楚，但**"长什么样"是视觉创作的活儿**——那需要审美判断和图像能力，不是我的强项。

所以下面是**简报（brief），不是规范（spec）**。里面**没有**"用什么颜色、什么字体、什么风格"的指令——那些位置留白给看山去探索。

### 4.2 设计简报

#### ① 产品是什么

一个音乐榜单数据分析工具。用户能查一首歌在榜单上的**完整轨迹**（空降、在榜、出榜、回榜），比较不同对象，看到新诞生的纪录，并把结果分享出去。

#### ② 用户是谁、什么心态

- **核心用户是"数据迷"**：他们会盯着数字看，会为一条反常的曲线兴奋，会截图发给同好。他们要的是**精确感和发现感**。
- **外围用户是歌迷**：只想快速知道"我追的歌手最近怎么样"，他们要的是**一眼看懂**。

#### ③ 使用场景（决定了主题与密度的取舍）

> 晚上十点，一个人躺在床上，单手刷手机，想看看自己关注的那首歌这周怎么样了。
> 白天，同一个人坐在电脑前，认真把两份数据摆在一起对比。

这两句话的含义需要看山自行判断：**夜间单手场景**与**白天桌面场景**的差异，会直接影响主题选择和密度设计。

#### ④ 必须传达的四种感觉（这是要求，不是风格）

| 要传达 | 因为 |
| --- | --- |
| **精确** | 用户是在看数字，任何含糊都会降低信任 |
| **可信** | 数据产品一旦显得"编的"，就全盘皆输 |
| **有发现感** | 用户来的目的是"看到有意思的东西"，不是"查一个数值" |
| **有生命** | 数据每天都在变，静态感会让人觉得这里没东西可看 |

#### ⑤ 信息层级（这部分由我定，请按此组织）

| 屏 | 第一眼 | 第二眼 | 第三眼 |
| --- | --- | --- | --- |
| **数据现场（首页）** | 今天最值得看的那件事 | 同类事件的列表 | 我的关注的变化 |
| **榜单轨迹页** | 曲线本身 | 关键数字（空降/峰值/在榜/回榜） | 明细、口径、AI 解读 |
| **歌手页** | 是谁、主场是哪个榜 | 汇总数字 | 名下作品列表 |
| **对比页** | 一句结论 | 图形 | 维度明细与权重控制 |
| **榜单列表页** | 前几名 | 涨跌变化 | 完整 50 首 |
| **我的** | 身份 | 统计 | 收藏与关注列表 |

#### ⑥ 必须覆盖的屏幕与状态（共 6 屏 × 6 类状态）

**屏幕**：数据现场 / 榜单轨迹 / 歌手页 / 对比页 / 榜单列表 / 我的

**状态**（每一屏都要有，不能只做正常态）：

| 状态 | 场景 |
| --- | --- |
| 空 | 首次进入 / 没有数据 / 搜索无结果 |
| 加载 | 骨架屏（**不要转圈**） |
| 错误 | 网络失败 / 资源不存在 |
| 边界 | 超长歌名、0 值、极大值、无空降、无回榜 |
| 权限 | 未登录 |
| 离线 | 断网 |

#### ⑦ 硬约束（这些不可协商）

1. **三层数据必须视觉可分**：【事实】【热点】【解读】需要三种一眼能区分的标记方式，且**不能只靠颜色**（需考虑色盲用户）；
2. **名次上升/下降**要有明确但不刺眼的视觉语言；
3. **深色优先，但必须可扩展到浅色**（结构上要为两套主题留出空间）；
4. **触达面积 ≥44×44px**；正文对比度 **≥4.5:1**（占位文字同样达标）；
5. **320px 宽度可用**，且任何宽度都不能出现横向溢出；
6. **数字必须等宽**（排名变化时不能抖动）；
7. **封面图**是重要素材（每首歌都有），视觉方案要考虑它怎么被自然地带进来。

#### ⑧ 反面清单（我不希望它变成这样）

| 不要 | 原因 |
| --- | --- |
| 金融软件那种密恐式全屏数字 | 用户是来看故事的，不是来盯盘的 |
| 大面积渐变、发光、霓虹 | 数据产品最忌讳"花" |
| 卡片简单堆叠成列表 | 会变成"哪里都能见到的后台界面"，没有记忆点 |
| 写实插画、3D、拟物 | 与"精确"的调性冲突 |
| 系统 emoji | 与专业感冲突 |
| 到处都用同一种强调色 | 强调色用多了就等于没有强调 |

#### ⑨ 期望的产出（分两步，先探索再深化）

**第一步：给 3 个视觉方向**

每个方向包含：一句气质描述 + 主色板 + 字体方案 + 一个关键屏（**榜单轨迹页**）的视觉稿。

> 为什么选轨迹页做验证：它是这个产品的核心价值所在——如果这个页面的视觉能撑住，整套系统就成立。

**第二步：选定方向后深化**

输出 6 屏的完整视觉稿 + 状态设计（空/加载/错误）+ 视觉资产包。

## 5. 内容与文案规范（这部分归我）

### 5.1 语气

**克制、精确、不煽情。** 这是数据产品的语气，不是营销号的语气。

| 这样说 | 不要这样说 |
| --- | --- |
| 这首歌空降第 3，一路掉出榜，第 11 期又回来了。 | 太离谱了！这首歌的走势简直逆天！ |
| 峰值第 1 名，连续 10 期未让出。 | 霸榜十周，无人能敌！ |
| 当前权重下：A 在 4 个维度领先。 | A 完胜 B。 |

### 5.2 术语统一表（全站必须一致）

| 概念 | 统一用词 | 不要混用 |
| --- | --- | --- |
| 上榜的完整序列 | **榜单轨迹** | 走势图 / 排名变化 / 曲线走势 |
| 首次进榜 | **空降** | 首次上榜 / 初次进榜 |
| 出榜后回来 | **回榜** | 重返 / 再次进榜 |
| 掉出榜单 | **出榜** | 落榜 / 掉榜 |
| 榜单的更新单位 | **期**（按榜单显示天/周） | 次 / 轮 |
| 数据的时间点 | **取数时间** | 更新时间 / 抓取时间 |

### 5.3 禁止用词（对抗性与误导性）

**禁止**：对线、对决、吊打、碾压、完胜、谁更红、谁更强、实锤、打脸、塌房。

**禁止的表述**：把"同期"说成"因为"；把"演示数据"说成真实数据；把外部榜单的名次和站内榜直接比较。

### 5.4 三类标准文案模板

**AI 解读（每条都要带标签）**

```
【事实】以第 1 名进榜，峰值第 1 名。
【热点】2026-10-04 · 格莱美相关活动表演片段被广泛转发（来源：示例热点）
【解读】近三期平均第 3 名，此前三期平均第 1 名，有所回落。
口径提醒：本条轨迹为演示数据；时间接近不等于因果。
```

**空状态（必须给出下一步，不能只说"暂无数据"）**

```
还没有收藏的走势
在任意歌曲的轨迹页点「收藏」，就能把这条走势留在这里随时回看。
[去看看数据现场]
```

**错误态（说明发生了什么 + 能做什么）**

```
数据没拉到，可能是网络问题。
[重试]  [看看已缓存的内容]
```

**关于模拟走势的诚实处理**：模拟就必须标注，否则会被当成真实历史。已在三处标注——

1. 轨迹卡头部：「单位「天」· 每日更新 · **模拟走势**」（琥珀色）
2. 指标卡下方：「空降位 / 峰值 / 在榜期数由模拟走势推算（末值锚定为真实当前名次），非真实历史数据。」
3. AI 解读：「本条走势为模拟生成（公开接口不提供历史回溯），末值锚定为真实当前名次，仅用于展示产品形态；真实历史轨迹需平台归档。」

榜单页底部也统一说明"缩略走势为模拟生成（公开接口不提供历史回溯），仅用于演示"。

**测试方法的一个漏洞（值得记住）**：此前所有测试都跑在 `http://127.0.0.1` 上，因此**从未覆盖 `file://` 场景**，而用户恰恰是用 `file://` 打开的。现已补一个专门跑 `file://` 的测试（`work/file-share-test.mjs`）作为回归保护。
